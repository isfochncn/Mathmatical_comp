# 四问代码实现路线与使用指南

> 本文件给出后续代码组织、算法路线、使用方式、利弊与选择建议，不是已实现的软件说明。文中目录、接口和命令均为建议设计，当前不保证存在或可运行。  
> 依据：四问建模规范、题意解析备忘录和仓库《代码实现风格》笔记。技术能力参考文末及相关段落的官方文档；未安装依赖、未检查商业许可、未读取附件工作簿、未进行性能测试。  
> 本轮不编写求解代码、不求解、不改变已有模型假设。后续先核验附件与结算规则，再冻结实现配置。

## 1. 总体选择建议

推荐统一使用Python，以Pyomo表达模型、HiGHS作为默认LP/MILP求解后端；有可用Gurobi许可且实测表明有必要时，再接入Gurobi。问题一可用SciPy做小型独立核对，但不建议为四问维护四套求解器接口。

Pyomo是建模层，不是求解器；HiGHS/Gurobi负责求解。HiGHS支持LP与MIP且采用MIT许可；Pyomo的APPSI接口面向反复修改同一模型的求解，适合作为滚动调度候选，但实际收益需测量。[HiGHS官方介绍](https://highs.dev/)、[Pyomo APPSI文档](https://pyomo.readthedocs.io/en/stable/reference/topical/appsi/appsi.html)。

四問共用数据、设备、账单、执行和校验模块，只切换“可用信息、合同权限、价格口径、终端条件”。首先完成可验证的确定性基线，再逐步增加预测和情景；这属于开发顺序，不把点预测近似改称多阶段随机模型。

## 2. 工具路线：怎么用、利弊与选择

以下性能判断是工程取舍建议，不是对本仓库的实测排名。

| 路线 | 使用方式 | 优点 | 代价/限制 | 选择建议 |
|---|---|---|---|---|
| Pyomo + HiGHS | 符号变量/约束建模，经HiGHS接口求解；重复模型优先评估APPSI | 与现有公式对应清楚；同一模型便于扩展；无商业求解许可依赖 | 建模层有开销；不是所有高级约束都能直接传给后端 | 四问统一主线 |
| SciPy + HiGHS | 用linprog或milp传入目标、边界和稀疏约束矩阵 | 简洁，适合标准LP/MILP和小型基准 | 矩阵行列映射容易写错；跨问扩展可读性较弱；不是原生高级逻辑接口 | 问题一核验或熟悉矩阵建模时选用 |
| Pyomo + Gurobi | 保留数学表达，换后端并核对约束转换与状态解释 | 可以比较后端，无需彻底改写业务模块 | 许可、接口适配与复现成本；不能承诺一定更快 | 现有模型通过校验后、有许可再测 |
| gurobipy直接建模 | 直接使用变量、约束、指示约束及多目标接口 | 更直接调用Gurobi特性，减少部分中间层限制 | 与供应商API耦合；换求解器需重写部分模型 | 团队已熟悉且确定使用Gurobi时可选 |

SciPy的milp提供混合整数线性优化并使用HiGHS后端。[SciPy milp文档](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.milp.html)。Gurobi提供指示约束与多目标API，但安装gurobipy不等于获得无限规模许可，随安装附带的许可可能限制模型大小。[Gurobi模型API](https://docs.gurobi.com/projects/optimizer/en/current/reference/python/model.html)、[许可说明](https://support.gurobi.com/hc/en-us/articles/29682074018833-What-does-Restricted-license-for-non-production-use-only-mean)。

辅助工具建议：NumPy处理求解数组；pandas用于读取后表格整理；openpyxl用于向现有模板副本定点填值；Matplotlib用于诊断图；pytest用于少量关键回归；配置可用TOML或YAML，选一种即可。具体依赖版本在首次环境验证成功后固定，不在未测试时写死版本号。

模板包含图形等复杂对象时，openpyxl不能保证完整往返保留，须检查副本并避免覆盖原模板；其官方文档明确说明并非所有Excel对象都能读取保存。[openpyxl教程](https://openpyxl.readthedocs.io/en/3.1/tutorial.html)。

## 4. 代码书写的具体约定

1. 数学符号可短，工程变量用语义和单位，例如`charge_kwh`、`price_actual_yuan_per_kwh`。统一`float64`量值，索引用整数/真实时间，不用浮点小时作键。
2. 交易为144段，SOC为145个边界；写出shape约定，不用隐式广播把不同维度凑到一起。0:00+1是边界，不是额外一笔交易。
3. 数据加载、数学建模、求解、复算、导出各有入口；优化器不要直接读取Excel或写结果文件。
4. 用轻量数据结构传递DayInput、ObservedState、ContractBook、Trajectory、Bill等概念；是否使用dataclass按实现需要决定。全套原始未来数据只交给仿真驱动，不交给策略接口。
5. 参数注明单位、来源和性质，集中保存效率、功率侧、初值、终端规则、结算模式、价格可见性。未决假设用明确枚举值，不使用含糊的`advanced=True`。
6. 对外返回求解状态、是否有可行解、目标、实际复算费用、最大残差、耗时及间隙；不要只返回一个购电数组。
7. 不把所有异常捕获后返回零数组；区分输入错误、不可行、无界、超时有解和超时无解。只有经过复算的可行解才能继续执行。
8. 注释说明效率所在侧、时间边界、计价原因和模型节号，而不是逐行复述语法；为关键约束命名，便于定位不可行原因。
9. 模型内部保留完整精度，展示时再舍入。非负修正只限明确数值容差，修正后重验守恒，不随意裁剪大误差。
10. 不在程序里写个人绝对路径；从配置或项目入口解析路径。交付文档可给清楚的本地链接，源码要能在其他目录运行。

## 5. 五个必须隔离的接口

| 接口 | 可以接收 | 不能承担的职责 |
|---|---|---|
| 数据标准化 | 原始附件、单位和时间语义 | 私自补上未来预测或修改题面规则 |
| 信息视图 | 当前时间、已发布预报、已完成实测 | 将当天剩余真实数据交给计划模块 |
| 计划/调整 | 当前信息、实际SOC、已有合同、模型配置 | 在非允许时点重签合同或修改历史 |
| 实际执行 | 当前合同、当前可见运行信息、真实当前SOC | 使用未来真实电价/负载择优当前动作 |
| 校验/导出 | 完整已执行轨迹、真实价、模板映射 | 从情景平均轨迹冒充实际执行结果 |

信息检查不只依赖一条assert。更可靠的设计是策略函数根本拿不到未来实测表；仿真层逐事件给它信息。光伏和价格同时保存发布时间与有效时间，预测模型也保留训练截止时间。

## 6. 问题一：确定性储能调度方向

建议入口职责为“读取附件1→标准化144段输入→生成确定性模型→求解→独立复算→导出result1”。输入是给定预测，不在这一问先训练预测模型。

第一版实现线性规划以检查能量平衡、效率、容量、功率和首末状态；再验证有无同时充放电。最终需要互斥或最小弃光次级目标时，用统一MILP约束，不以正电价代替可执行性检查。

可用一个2—4时段手工构造例子验证低高价、效率损耗和首末状态，再上144时段。使用SciPy独立实现仅需覆盖这一小型数学核对，不必复制全部业务流程。

优点是调试范围小、可定位公式错误；局限是对给定预测可行不代表对真实光伏偏差也可靠。问题一验证通过后，冻结物理模块，后续只增加交易与信息结构。

## 7. 问题二：日前固定计划与因果运行方向

先实现“历史同刻或季节性点预测→0点生成x→日内固定x→逐段储能运行和紧急补购→实际SOC跨日继承”。这是点预测滚动基线，未完整度量不确定性，必须与规范中的条件场景主模型分开命名。

第二步才增加预测误差与有限条件场景。实际回测每次只执行当前动作，不把各情景全日最优轨迹挑一个当作真实策略。

代码重点是x、s、u三者分开；计费使用x而不是x-s。1月冷启动/预热保存实际轨迹，2月1日初始电量可追溯。逐日连续运行，不把每一天作为可独立重置6000的样本。

优点是先获得完整可运行参照，再判断场景是否改善实际成本；局限是点预测可能低估紧急购电风险，场景模型则增加构造、因果约束与计算负担。

## 8. 问题三：预报事件驱动的合同调整方向

在问题二驱动上新增0/6/12/18预报事件。x只读保存，每个y版本保存发布时间和作用范围，最终有效合同由版本规则重建。非发布时刻运行层只能改充放电和紧急量。

首先把结算写成独立的数值函数，验证R/N以及100→120→80等文档算例，再写对应优化表达。独立复算函数应从原x和最终y重算，不直接读取优化目标值；两者共享规则参数，不共享求解器表达对象。

先实现“使用当前已发布预报的滚动优化”近似；之后再加入未来预报更新的条件分支。附件3中将来才发布的版本只由仿真驱动到时释放。

优点是事件清楚、版本可审计、方便比较更新子集；局限是退款和重复修订口径会直接影响策略，未核验规则不能靠代码默认值掩盖。简化滚动策略也不能声称精确计算了未来信息价值。

## 9. 问题四：价格预测与双分支复用方向

复用问题二/三，新增价格信息视图与真实结算价。4-2维持固定合同，4-3保留允许调整时刻；不因价格每段更新而扩展合同交易权限。

第一步运行因果价格点预测；第二步生成负载—光伏—价格联合场景。决策接收预测/已公布价，账单接收真实结算价，分开函数参数以防误用。

在进入模型前检查价格符号。负价触发模型适用性审查，而不是用正价的辅助上界裁掉不方便的数据。4-2是否读取附件3在实验配置中明确。

优点是复用度高且可清晰隔离价格影响；局限是价格相关性、发布时间、浮动/锁价口径可能比求解器选择更影响结论。不能把固定价费用与波动价费用之差直接称为算法节省。

## 10. 预测方法怎么选

| 方法方向 | 使用方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| 历史同刻/相似日/季节性基线 | 仅用过去日期同时间段形成负载、光伏或价格预测 | 易解释、冷启动负担较小、便于检查泄漏 | 突发变化和极端天气/价格响应较弱 | 先实现，作为所有改进的参照 |
| 带滞后和日历特征的回归或树模型 | 特征只取决策前已知量，按日期滚动验证 | 能表示部分非线性和时间特征 | 特征泄漏、调参和极端误差风险 | 基线不足且历史量支持时再加 |
| 现有光伏预报加历史误差校正 | 问题三/4-3按发布时间和提前量校正附件3 | 利用已有预报，不必从头预测光伏 | 同有效时刻不同发布版本容易混淆 | 优先于另造复杂光伏预测器 |
| 深度时序模型 | 在严格时间划分下训练并与简单模型对照 | 数据足够时可能捕获复杂关系 | 样本、计算和调参成本较高，当前未证实必要 | 暂不作为第一选择 |

验证按日期和预测发布批次组织，不能随机打散10分钟行。即使用TimeSeriesSplit，也要保证训练标签在验证决策时已成熟，必要时设置gap或自定义日期分组，避免同日/同一有效时刻不同预报版本跨集合。[TimeSeriesSplit官方文档](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)。

模型选择看预测误差，也看进入闭环后的实际费用和紧急量；不能用全年费用挑选参数，再把同一全年称为独立测试。

## 11. 优化方向的利弊和使用边界

| 方向 | 如何使用 | 优点 | 局限 | 建议 |
|---|---|---|---|---|
| 确定性LP/MILP | 当前点预测作为输入求解 | 最容易调试，计算规模可控 | 未显式描述预测风险 | 问题一主线；后续各问第一版基线 |
| 当前预测滚动优化 | 观测更新后重算未来，只执行当前动作 | 贴近因果运行，开发成本适中 | 终端与预测近似可能短视 | 问题二—四先用它跑通 |
| 有条件分支的随机MILP | 联合场景按时间揭示，节点共享动作 | 可表达紧急成本与未来信息 | 场景树大、联合分布和非前视约束难 | 基线已验收且性能允许后升级 |
| 鲁棒/风险约束扩展 | 在有依据的不确定集合或风险准则下优化 | 可强调极端缺口控制 | 可能保守，新增参数改变原目标 | 仅作为另设对照，不默认替换主模型 |
| 遗传/粒子群等启发式 | 用作少量外层策略参数搜索并严格时序验证 | 适合部分难解析外层问题 | 易违反储能约束，通常不能证明最优 | 不作为已有线性/混合整数内层调度的首选 |

开发简化不能偷偷删约束。减少场景、缩短时域或减少优化频率均需新实验标签和验证，不以“代码优化”为名改变合同权限、效率、初末状态或结算。

## 12. 性能、缓存与续跑建议

每个334天分支逐10分钟求解约334×144=48,096次，尚未计0点和发布节点的独立优化。若单次耗时1秒，仅该部分约13.4小时；这只是规模估算，不是机器实测。

先测“一个代表日→连续一周→全年”，分别记录数据转换、建模、求解、校验和导出耗时。不要先对全年度启动庞大场景树后才发现无法完成。

- 只读一次Excel，标准化后在内存或带来源指纹的缓存中复用；每段不重新打开工作簿。
- 模型结构相同时评估参数更新/持久接口，别每次构造全部不变约束；场景拓扑变化时需要正确重建，不能错误复用。APPSI的用途见前述官方文档。
- 先用少量场景评估误差与耗时；增加规模只有在实际收益或稳定性改善时才有依据。
- 每日保存检查点：实际末SOC、当前配置、已完成日期、训练可用截止、随机状态或可重建种子及实际结果路径。
- 恢复运行必须核对输入指纹与配置；旧缓存不能在效率或结算改动后直接接着用。
- 连续日期存在SOC依赖，不宜逐日并行。可并行独立策略/参数实验，但每个实验内部按时间运行，避免进程数乘求解器线程数造成过度占用。
- 热启动不等于保证加速，也不是复用旧解免检；限时解只有存在可行 incumbent 且通过复算才可执行。

第一版不承诺每段重算大规模树。可用轻量因果运行策略作明确对照，但不得与完整滚动模型混称。

## 13. 最小而有效的验证集合

| 检验 | 要抓住的错误 |
|---|---|
| 2—4时段能量与效率手算 | kW/kWh混用、效率放错侧、初末状态透支 |
| 固定计划过剩和缺口 | s与r混用、紧急量重复计费、购电费用按接收量错误减少 |
| R/N及多版本账务算例 | 退款遗漏、调整总量当增量、重复收费 |
| 发布时刻前后边界 | 6点预报改写5:50区间、未来有效值提前可见 |
| 冻结当前信息后替换未来真实数据 | 当前计划是否意外读取未来；固定种子避免随机变化干扰判断 |
| 跨日续跑与不中断运行比较 | SOC重置、检查点缺失、随机轨迹变化 |
| 重复电价/关闭调整的退化 | 四问共享模型是否真的一致；比较时同步信息和终端条件 |
| 模板回读与原轨迹汇总对照 | 144/145错位、单位、总量/差额、表格漏行 |

容差区分电量kWh、费用元、相对求解间隙，不用一个epsilon控制所有量。数据不可行、未定义负价机制、未来信息泄漏必须使正式导出失败，而不是仅打印警告继续输出。

场景最优、限时可行、退化基线及回退策略分别记录，不把所有状态统一写成optimal。原始轨迹、账单和验证摘要保存后，再生成图表和工作簿。

## 14. 拟议使用方法与交付说明

以下命令是未来CLI的接口设计示例，**当前没有实现microgrid入口，不能直接运行**。实现时可改命令名称，但应保留先审计、后运行、再验证/导出的顺序。

```text
python -m microgrid.cli audit --config configs/problem1.toml
python -m microgrid.cli run --problem 1 --config configs/problem1.toml
python -m microgrid.cli run --problem 2 --config configs/problem2.toml
python -m microgrid.cli run --problem 3 --config configs/problem3.toml
python -m microgrid.cli run --problem 4-2 --config configs/problem4_2.toml
python -m microgrid.cli run --problem 4-3 --config configs/problem4_3.toml
python -m microgrid.cli validate --run-dir outputs/示例运行目录
python -m microgrid.cli export --run-dir outputs/示例运行目录
```

使用流程建议：

1. 后续实现完成后创建独立环境，按项目实际固定依赖安装；先验证求解器可运行小型LP/MILP，Gurobi另查许可，不因可导入就认定可解正式模型。
2. 在配置中填写附件路径、采样语义、效率与终端、结算和价格信息规则；audit输出假设和输入摘要，未决必填项不能悄然默认。
3. 先跑问题一，再跑一个连续短窗口及其状态预热；短窗口起点必须有初始状态来源，不随意从任意日期以6000开始。
4. 短窗口通过后跑全年；失败后从匹配配置的检查点恢复，不手工拼接不同假设的结果。
5. validate通过后，export向模板副本写入；正式文件固定为result1、result2、result3、result4-2、result4-3.xlsx，按分支生成。
6. README记录实际测试的环境版本、命令、输入/输出、预计耗时范围、随机性和已知限制；未实测时间写“待测”，不填承诺值。

每次run目录建议包含：配置快照、输入指纹、环境版本、计划/版本记录、实际轨迹、费用分项、验证摘要和求解日志。最终图表从这些结果自动汇总，禁止从图上抄数回填工作簿。

## 15. 最终代码方向与选择建议

| 阶段 | 优先代码方向 | 使用场景 | 主要收益 | 主要代价 | 建议 |
|---|---|---|---|---|---|
| 共同基础 | 数据审计、physics、settlement、因果信息视图 | 四问全部 | 一处修正全局一致，减少重复错误 | 前期要明确接口 | 先完成 |
| 问题一 | 确定性LP核验及必要的MILP互斥 | 给定预测的单日调度 | 快速验证物理模型 | 不能覆盖真实预测偏差 | 第一份可运行程序 |
| 问题二 | 点预测+固定计划+因果运行，再加场景 | 计划与紧急成本权衡 | 能逐步完成全年闭环 | 多日状态与风险建模增加工作量 | 第二步实现 |
| 问题三 | 事件驱动合同版本+独立结算+滚动优化 | 多次光伏预报调整 | 可审计更新行为与经济价值 | 结算歧义和版本管理最易出错 | 账务用例先于优化 |
| 问题四 | 价格信息层+4-2/4-3复用 | 波动电价下两种交易制度 | 可隔离价格风险与调整价值 | 价格可见性、相关性及负价边界 | 前三问稳定后扩展 |
| 性能升级 | 小规模条件树、持久求解接口、独立实验并行 | 基线耗时或风险表现不足 | 有针对性提升计算/策略能力 | 需要额外验证且可能无收益 | 实测后选，不预先堆叠 |

默认组合为Python + Pyomo + HiGHS，先确定性/点预测闭环，后联合场景；已有合适Gurobi许可时以同一模型和数据实测比较。先保证物理、信息和费用三方面正确，再讨论复杂预测或更大场景规模。
